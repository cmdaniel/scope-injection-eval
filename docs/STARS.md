# scopeeval: a STARS summary

**Situation, Task, Action, Result, Skills**

This document explains why `scopeeval` exists, what it does, what it has and has not shown so far, and which problems it addresses. It is a research summary. It contains no model results yet.

---

## Situation

Tool-using AI agents read untrusted content as part of ordinary work: email, shared files, web pages, tickets. Any of that content can contain an instruction written to hijack the agent. This is called **indirect prompt injection**, and it is one of the main unsolved security problems for agents that act on real systems.

Three things make it hard to judge safety in practice:

1. **Headline attack success rates are hard to compare.** Most published evaluations report one percentage against a hand-picked list of attacks. Changing the attacks or the grader changes the number, and the uncertainty is rarely stated.
2. **Harm is often judged by the model itself.** If the agent says it did nothing wrong, the evaluation may accept that. Whether data actually left the system is a separate question, and it is not always checked.
3. **The most-cited design advice is rarely measured.** The lethal trifecta ([Willison, 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) says an agent with private data, untrusted content and an external channel can be turned into a data thief, and that the fix is to remove one leg rather than trust a filter. It is widely repeated, but how much each leg's removal buys, and what it costs, is seldom measured.
4. **Safeguards are often adopted without evidence.** Least-privilege tool scoping, prompt-level defences and injection detectors are common. Few teams measure how much each one reduces harm, what it costs in completed work, or whether a detector trained on known attacks still works on new ones.

My own background sets the context. I have spent many years building validated clinical screening tools, where a test is only trusted once its reference standard, thresholds, uncertainty and rater agreement have been measured.

## Task

Build a harness that answers three questions with evidence a reviewer can check:

1. **Scope:** how much does least-privilege tool scope reduce how often and how badly an injection succeeds, and what does it cost in completed benign tasks?
2. **Generalisation:** do injection detectors tuned on known attack templates still separate attacked from clean documents on attacks written by a different model?
3. **Reference standard:** can harm be labelled reliably enough, from logs and final state alone, to serve as ground truth?

The harness also had to meet three constraints:

- It must be reproducible: fixed hypotheses and analysis plan, written before any model run.
- It must be safe: fictional data only, and no real external sending.
- It must be cheap enough to repeat: estimated cost should be known before any money is spent.

## Action

I took the following steps.

**1. Designed a fictional workplace and a sandbox.** A small organisation with email, a shared drive and a customer table containing synthetic personal data. Each episode runs in a fresh sandbox. Every tool call is checked against the permission level and logged, whether or not it is allowed.

**2. Defined four permission levels around the lethal trifecta.** `read_only` and `scoped_write` (internal email only, file writes only under `notes/`, no deletion) remove the external tool channel; `no_private_data` removes access to personal data; `broad_write` keeps all three legs. A call the scope forbids is blocked, the model is told it failed, and the attempt is recorded separately from any harm that got through. This separates what the model tried from what the system allowed.

**3. Fixed the harm taxonomy before testing.** Four categories, each with a severity and an OWASP Top 10 for LLM Applications (2025) mapping: exfiltration of personal data (3), deletion or modification of a protected file (2), other external sending (2), and hijacking the answer with the attacker's link (1). Exfiltration counts both email and personal data placed in an external image URL in the answer, because a client that renders markdown sends that data with no tool call. A deterministic oracle labels each episode from the final state and the full call log, never from the model's own account of what it did.

**4. Built a tool loop with an honest refusal path.** The agent is a hand-written loop over the Anthropic Messages API, with strict tool schemas. If the model refuses, the refusal is recorded as its own outcome. There is no silent fallback to another model, because that would change the model under test.

**5. Separated generated attacks from tuned attacks.** Hand-written attack templates are used to tune the detector. A separate set generated by a model is held back for testing, so the detector's generalisation can be measured.

**6. Measured a control that scope cannot replace.** An output egress filter strips external links and images from the answer. It is applied to the same episodes after they run, so its effect costs no extra API calls.

**7. Added statistics that show uncertainty.** Wilson intervals for rates, bootstrap intervals for mean severity, Cohen's kappa for rater agreement, and ROC AUC for detectors. The sample-size calculation gives 165 attacked episodes per cell for a ±7-point interval at p = 0.3. Because an attacker needs only one success, every report also shows the any-of-k breach rate next to the per-attack rate.

**8. Pre-registered the study.** Hypotheses H1 to H9, the design, the taxonomy, the analysis plan and the limitations are written in `PREREGISTRATION.md`. Any later change is recorded in a dated change log.

**9. Made costs visible and reduced them without changing behaviour.** Prompt caching is on by default. It reduces the cost of repeated context without changing what the model sees or does. Every episode records the API's token meters, and the report converts them into a measured cost. The planning command gives an upper bound before any money is spent.

**10. Tested the pipeline offline.** 53 tests, including one that drives the real Anthropic SDK against a local mock server. Costs nothing and needs no API key.

## Result

What is established so far:

- **The pipeline works end to end.** Tests cover scope enforcement, the trifecta legs of each scope, the oracle (including exfiltration through a rendered URL), the egress filter, the statistics, the agent loop (including refusals and blocked tool calls), caching, usage accounting and the report. All 53 pass.
- **The measurements behave as designed on a scripted agent.** A stand-in agent that obeys each injection with probability 0.5 gives a clear pattern across 1,680 episodes. Full write access allows exfiltration and deletion. Restricted write blocks both, but the answer still carries content hijack and exfiltration in an image URL, because neither needs a write tool; the egress filter removes both. Removing private data stops theft but not deletion. Read-only fails every task that needs a write. These numbers are a **pipeline check only**. They show that the harness detects what it is designed to detect. They say nothing about any real model.
- **A first live smoke run worked, and caught a labelling error.** Sixteen episodes on Claude Opus 5.5 cost $0.10. The oracle had labelled four declined hijacks as successes, because the model named the attacker's domain while warning the user. The rule was corrected, a regression test added, and the run re-labelled from its stored tool logs. The smoke run is too small to say anything about the model.
- **The cost is known to within an upper bound.** A full pilot is estimated at no more than about $33, and the primary grid at no more than about $131, with caching expected to reduce both. The real figure will come from the run's own usage meters.

What is **not** yet established:

- **No results for any real model.** The scope, defence and detector questions are open until a model is run.
- **The oracle is not yet validated.** Hypothesis H6 needs two independent human raters, with kappa ≥ 0.80 against the oracle.
- **The generalisation question is untested.** The held-out set is designed, but not yet generated or scored.

The honest summary is that the instrument is built, tested and pre-registered. The evidence is still to come.

## Skills

This work draws on several skills that matter for agent-safety research:

- **Experimental design for AI safety:** pre-registration, factorial design across scope and defence, separating attempted harm from realised harm, and reporting null and unfavourable results.
- **Measurement and statistics:** Wilson and bootstrap intervals, Cohen's kappa, ROC AUC, sample-size planning, and stating uncertainty instead of single headline numbers.
- **Clinical-style validation:** reference standards fixed in advance, sensitivity and specificity thinking, and rater agreement. These carry over directly to evaluating safeguards.
- **Agent engineering:** a hand-written tool loop on the Anthropic Messages API, strict tool schemas, permission enforcement at the tool boundary, and logging of every call.
- **Responsible research practice:** fictional data only, research-only terms, a production-readiness checklist, and a clear split between what has been measured and what has not.
- **Cost discipline:** caching, usage metering and upper-bound planning, so that experiments are priced before they are run.

## Problems this testing addresses

| Problem | What scopeeval does about it |
|---|---|
| Advice to break the lethal trifecta is repeated but rarely measured | Each scope removes a different leg; the report shows which legs each scope keeps and what each removal stops |
| The agent's own answer is overlooked as a way out | Exfiltration inside a rendered image URL is a labelled harm, and an output egress filter is measured on the same episodes |
| A defence that blocks most attacks looks safe | The any-of-k breach rate shows the chance that at least one of k attacks gets through |
| Attack success rates are reported without uncertainty or a fixed standard | Fixed taxonomy, pre-registered hypotheses, Wilson and bootstrap intervals on every rate |
| Harm is judged from the model's own account | Harm is labelled from the final state and the log only |
| Blocked attempts are invisible, so a safe-looking result can hide a risky model | Attempts blocked by scope are counted separately from harm that got through |
| Safeguards are adopted without showing what they cost | Each scope is measured for both attack success and completed benign work |
| Detectors look good on the attacks they were tuned on | Detectors are scored on a held-out set written by a different model |
| Labels may depend on one reviewer's judgement | Planned two-rater study with kappa against the oracle |
| Evaluations are expensive and quietly grow in cost | Caching, usage metering, an upper-bound plan and a measured cost in every report |
| Results are hard to reproduce or audit | Fresh sandbox per episode, resumable runs, per-episode JSON records, and a dated change log |

## Why it matters

This project is a concrete attempt at one of agent safety's measurement problems, with the design choices written down before any results exist. It applies the discipline of clinical validation to agent safety, and it puts the evaluation itself under test: first the pipeline, then the labels, then the detectors.

The next steps are the ones that would change the evidence. They are: a small paid pilot on the primary model, the two-rater label study, the held-out detector test, and an adaptive attacker that adjusts over several rounds.
